- Status: Volume II Implementation Architecture Pass 001

## Enforcement Layers

Every protected request crosses these controls in order:

1. TLS termination and host validation;
2. request-size/content-type and same-origin controls;
3. Session or scoped service identity authentication;
4. safe transaction-local PostgreSQL tenant context;
5. the exact Volume I effective-authorization evaluator;
6. aggregate/query object authorization;
7. Evidence Classification and field redaction;
8. database RLS and composite tenant foreign keys;
9. authorized DTO/presenter output controls;
10. immutable authorization/audit evidence.

No layer treats success at another layer as proof. RLS prevents accidental cross-tenant row access but never replaces action/field authorization. Hidden UI controls never replace server checks.

## Browser Session Transport

The physical Session credential is a 256-bit value generated by the operating-system CSPRNG and encoded as unpadded base64url. The raw value exists only in the browser cookie and the current request's filtered memory. PostgreSQL stores its SHA-256 lookup digest in `sessions.token_sha256` and an authenticated-encryption replay capsule as defined below; ciphertext is not an authentication lookup value.

The cookie contract is exact:

| Attribute | Value |
| --- | --- |
| Name | `__Host-f1_session` |
| `Secure` | true in every deployed environment except isolated local HTTP test |
| `HttpOnly` | true |
| `SameSite` | `Lax` |
| `Path` | `/` |
| `Domain` | absent |
| Browser expiry | Session absolute expiry; it is never extended |

Creating a fresh Volume I Session creates a fresh token. Exact replay of any Session-creating command returns the existing Session and MUST reissue that same credential while the Session remains active; it MUST NOT rotate the token, create another Session or depend on the browser having received the first response.

To make response-loss replay implementable, `sessions` MUST add nullable `token_replay_ciphertext`, `token_replay_nonce` and `token_replay_key_version`. At Session creation, AES-256-GCM encrypts the raw token using the current versioned platform Session-replay key and additional authenticated data containing Session, Account and Organization IDs, issue/absolute-expiry instants and `token_sha256`. Normal authentication never decrypts the capsule; it hashes the presented cookie and performs the digest lookup. Only the exact command-replay path may decrypt it, after current replay reauthorization and an authoritative check that server time is strictly before both Session expiries and the Session remains active. Digest mismatch or authentication-tag failure is a security incident and returns no credential.

The versioned Session-replay key ring is a platform boot secret shared by web processes. New Sessions use only the current key. A retired key remains decrypt-capable until every Session issued under it has terminalized or reached absolute expiry, then is destroyed. Session revocation or expiry atomically nulls its replay ciphertext, nonce and key version. A replay of a terminal Session returns the currently authorized/redacted stored Session result without a credential and clears any cookie. The decrypted token buffer is filtered and overwritten after the response header is constructed.

The PostgreSQL Session row contains exactly those three encrypted-replay fields in addition to `token_sha256`. Storing plaintext, placing the capsule in a command result/API body, deriving a token from Session identifiers, or creating a replacement token on replay is prohibited.

Accepted request activity changes only the server-side idle fields required by Volume I; it does not change the token, capsule or browser expiry. Session refresh and renewal do not exist.

Revocation through an already defined Account/Organization/security lifecycle, timed expiry, and an invalid token clear the browser cookie in the response when one is available. Clearing a cookie is not the authoritative revocation; the terminal database state is. Volume I defines no standalone current-user sign-out or Session-revocation command, so Volume II MUST NOT add a sign-out endpoint, control or inferred revocation permission; this remains `UPSTREAM-V1-SESSION-REVOCATION-002` in [APPLICATION_LAYER.md](APPLICATION_LAYER.md#upstream-v1-session-revocation-002).

Session lookup uses a constant-shape digest query. Logs, exceptions, traces, analytics and support tools MUST NOT contain the raw token, cookie header or full digest.

## Receipt-Bound Entry Transport

The managed-identity callback never places a receipt, provider code or command capability in a URL. It creates a 256-bit operating-system-CSPRNG entry handle, stores only its SHA-256 digest with the server-side Identity Validation Receipt and exact purpose/Organization/invitation/logical-return binding, and sets the raw handle in `__Host-f1_entry` with `Secure`, `HttpOnly`, `SameSite=Lax`, `Path=/`, no `Domain`, and a 30-day browser maximum. The handle is not an F1 Session and is accepted only on `/start`, `/invitations` and the corresponding receipt-bound `/api/v1` commands.

Before receipt expiry, the handle can construct only the one exact-purpose command permitted by the bound receipt. On the first accepted command it is atomically bound to that command ID, idempotency identity and canonical request hash. After receipt expiry or consumption it authorizes no new command, but while the retained command result exists it may locate only a byte-identical exact replay; altered input fails without disclosing the retained target. A successful response clears `__Host-f1_entry`; response loss leaves it available for replay. Server retention, not cookie presence, is authoritative, and an unconsumed expired entry cannot be revived.

Receipt-bound forms use a separate masked CSRF token. The base secret is HMAC-SHA-256 keyed by the raw entry handle over `f1-entry-csrf-v1`, receipt ID, uppercase method and normalized same-origin action. It follows the same Rails-compatible random masking and constant-time verification rules as Session forms. A Session CSRF token and an entry CSRF token are never interchangeable. Starting a new managed-identity flow replaces the browser entry cookie and does not invalidate an already committed command result.

## Authenticated Request Transaction

`Platform::AuthenticatedRequest` implements the in-transaction stage in [APPLICATION_LAYER.md](APPLICATION_LAYER.md); `Platform::UnitOfWork` is the sole transaction owner. Candidate Session lookup before the transaction is nonlocking and nonauthoritative. Inside the unit of work, proved context is established, then the Organization row is locked at tier one and Account/Session rows at tier two before any higher-tier target. It evaluates the idle and absolute deadline using database UTC time and commits terminal expiry before returning an expired result. Concurrent requests on one Session serialize their activity update by row lock; distinct Sessions never lock one another solely because they share an Account.

The authorized query or command fully materializes its DTO/result before commit. View rendering, JSON serialization, Turbo rendering, object upload/download and provider calls occur after commit with no Active Record object or lazy query retained.

The fixed security prelude/epilogue budget is at most eight SQL statements for Session lookup/lock, Account/Organization resolution, assignment/policy resolution, Authorization Decision, audit and Session activity. A workflow needing Support Session or protected-approval resolution may use four additional statements and MUST declare that in its query/command spec.

## CSRF, Origin And Cross-Origin Policy

Every cookie-authenticated non-safe HTTP request requires a Rails-compatible masked per-form authenticity token bound to the current Session, effective normalized request method and exact normalized form action. For a browser twin carrying the sole permitted `_method=delete`, the effective method is uppercase `DELETE` after Rails/Rack method override, not the physical `POST`; every other browser twin uses uppercase `POST`. Token rendering and verification apply that same effective method. Rails origin checking is enabled. A missing, invalid, reused-across-Session or cross-origin token fails before command construction and produces no product mutation.

F1 does not create a second Rails session cookie or store a CSRF secret column. For the current request only, the CSRF storage strategy derives a 256-bit Session base secret as HMAC-SHA-256 keyed by the raw Session token over `f1-csrf-v1`, the canonical Session UUID and `token_sha256`. It derives the per-form token from that base using the uppercase method and Rails-normalized same-origin path, then applies the standard Rails random one-time mask. Verification recomputes after Session authentication and uses constant-time comparison. Query strings, fragments, Host input and a client-supplied target do not enter the normalized action. A token rendered for one method, action or Session is invalid for another.

Turbo forms submit their hidden per-form token. A same-origin first-party JSON mutation receives an action-specific masked token in its authorized rendered bootstrap/form DTO and sends it through `X-CSRF-Token`; there is no origin-wide reusable meta token. `GET`, `HEAD` and `OPTIONS` MUST NOT invoke a product command; their mandatory Session activity, authorization/audit, low-cost usage checkpoint or named read event does not make them mutation endpoints.

Baseline browser APIs do not permit cross-origin credentialed requests. No wildcard or reflected CORS origin is configured. Machine service ingress and provider webhooks use their own signed authentication, reject browser Session cookies, and do not bypass tenant/action authorization after authentication.

The managed-identity return is the sole Session-CSRF exemption: the fixed cross-site `POST /auth/callback` accepts only the exact `f1-managed-identity-redirect-v1` form and validates its canonical F1 Host/scheme, one-time state/nonce flow binding, receipt purpose/audience, issuer/key/signature and expiry before creating a receipt-bound entry. It neither requires nor trusts an `Origin`/`Referer` header or any cookie. Every other callback method, origin-selected redirect, parameter shape or user-supplied return URL is rejected.

Every HTML, Turbo and first-party JSON response applies:

```text
X-Content-Type-Options: nosniff
```

The Content Security Policy is generated with a fresh response nonce:

```text
default-src 'self';
base-uri 'self';
object-src 'none';
frame-ancestors 'none';
form-action 'self';
script-src 'self' 'nonce-<response-nonce>' 'strict-dynamic';
```

The CSP builder substitutes the deployment's validated canonical F1 host; it never reflects an arbitrary request Host. Importmap and Rails-generated script tags receive the nonce. Inline event handlers, `eval`, dynamically constructed script text, inline style attributes and third-party browser scripts are prohibited. Turbo's default inline-style progress bar is disabled in favor of a class-based accessible request indicator. A required future browser origin needs an architecture/security change and CSP test; it is not added ad hoc.

Protected HTML/Turbo/JSON responses use `Cache-Control: private, no-store`, `Pragma: no-cache`, and `Vary: Cookie`. Authentication and authorization failure bodies contain no protected partial or existence-revealing alternative.

## Authorization And Redaction

`IdentityAccess::Public::Authorize` is the sole effective-authorization implementation. It executes the exact first-match/order contract in Volume I and returns one immutable decision. Every controller, command, query, job and external-effect checkpoint supplies explicit actor/service, Session when human, Organization, nullable Project, action, resource, support scope and classification requirement.

Authorization is never inferred from:

- Rails controller/action names;
- an Active Record association existing;
- a visible navigation item;
- an opaque UUID;
- a cached prior allow;
- an OrganizationMembership view alone;
- possession of an Export/object URL;
- a Sidekiq queue or job class.

For queries, execution order is authenticate and bind tenant; authorize object; load projection; authorize/redact fields; freeze AuthorizedDTO; commit; present. Presenters cannot restore omitted fields. Multiple-role classification follows Volume I's strongest independently allowing ceiling, not the union of every role.

Every background job reauthorizes its scoped service identity and current Organization/resource policy immediately before each named durable side effect. Suspension, revocation or scope contraction stops before the next side effect even if a job was queued earlier.

## PostgreSQL Tenant Context And RLS

### Safe context establishment

Application code MUST NOT set `app.organization_id` directly. It calls one reviewed `SECURITY DEFINER` database entry function for exactly one context type:

- human Session context;
- tenant-scoped service identity context;
- pre-Organization bootstrap-principal context;
- approved per-Organization support/investigation context.

The function validates the Session/service/bootstrap/support record, scope and current state, then sets transaction-local identity values plus an unforgeable context proof derived inside the database from the transaction ID and validated identities. The proof key is readable only by the schema owner. A raw `SET app.organization_id` without a valid proof therefore matches no RLS policy.

`f1_current_organization_id()` is a `STABLE`, `SECURITY DEFINER` helper with pinned `pg_catalog` search path. It returns a UUID only when the context proof validates and the Organization setting is a canonical UUID; absent, blank, malformed or unproved input returns `NULL` and never raises a cast error. Equivalent helpers return the validated actor/service/bootstrap/support identities.

Connection checkout and check-in run `RESET ALL` plus an assertion that no `app.*` value remains. Every repository call asserts an open transaction and validated context. A missing context produces no tenant row, not an unscoped query.

### Table policy classes

| Policy class | Tables | Runtime access |
| --- | --- | --- |
| Tenant | every `T-IMM`/`T-MUT` row and any nominally global table row with nonnull `organization_id` | `FORCE ROW LEVEL SECURITY`; `USING` and `WITH CHECK` require exact validated Organization |
| Project | every Project-owned tenant row | Tenant rule plus same-Organization composite Project FK; application also authorizes Project/resource |
| Bootstrap | identity receipt nonce, Bootstrap Grant and pre-Organization command/idempotency/result/audit rows | only validated bootstrap-principal proof and approved bootstrap service operation |
| Global release | Check Catalog/Definition and signed release artifacts | runtime `SELECT` only for active, integrity-verified versions; mutation only release service through reviewed function |
| Global restricted registry | audit/event/provider registries, global dedup identities and schema control | no direct runtime `SELECT/INSERT/UPDATE/DELETE`; reviewed functions perform minimal insert/lookup |
| Cross-Organization security bridge | platform Incident/Investigation bridges, LegalHold/deletion control rows | SecurityOperations/DataLifecycle functions; tenant data is processed one Organization-authorized transaction at a time |
| Sanitized operations | explicitly created operational views | `f1_readonly_ops` `SELECT` only; no identifiers/payloads beyond the view contract |

Every tenant table has an automated assertion for RLS enabled/forced, exact policy expression, `WITH CHECK`, composite FKs and absence of `BYPASSRLS`. `f1_runtime` owns no table and receives no blanket schema/table grant. Migrations run only as `f1_schema_owner`; application traffic cannot assume that role.

RLS tests exercise two Organizations, same UUID-shaped resource IDs, missing/malformed/forged contexts, bootstrap, service, support and cross-Organization paths for `SELECT`, `INSERT`, `UPDATE`, `DELETE`, joins, subqueries, background jobs and connection-pool reuse.

## Secret And Credential Handling

Platform boot secrets are injected through Heroku's managed secret configuration and are absent from source, images, database dumps and generated documentation. Tenant/provider Credential material is stored only in AWS Secrets Manager and selected by exact Secret ARN plus VersionId as fixed by [INTEGRATION_CONTRACTS.md](INTEGRATION_CONTRACTS.md); it is never copied into a Heroku config variable. PostgreSQL stores the ARN, VersionId, digest, type and lifecycle version defined by the schema.

Only an adapter execution may exchange an authorized Credential/material reference for a use-scoped in-memory lease. The resolver validates Integration/Credential/material state, purpose, adapter policy/version and deadline. The lease:

- is not serializable;
- is never a job argument, DTO, command, event, audit field or cache entry;
- cannot be requested by a presenter/controller/domain object;
- is released and its buffer overwritten after the one provider operation;
- never exposes a provider SDK credential object across the adapter port.

Rotation activates a new material version atomically with the Credential pointer. A worker resolves the current authorized version at the provider checkpoint; queued work never embeds secret material. Revoked/expired material fails closed under the existing Volume I reason mapping.

Rails parameter filtering and telemetry processors remove at least: Cookie/Authorization headers, authenticity tokens, Session tokens/digests, identity receipts/assertions/nonces/subjects, Invitation opaque references, normalized email, Credential/material references, provider authentication/signatures, Mailgun message body, AI prompts/responses where restricted, Evidence payload, Export object keys and presigned parameters. Redaction is tested against logs, traces, errors, job payloads and audit payloads.

## Cache Architecture

Queue Redis and cache Redis are separate managed services. Sidekiq alone uses queue Redis and owns `f1:sidekiq:*`; no web cache or application value uses it. Rails cache uses cache Redis under `f1:cache:v1:*`. No Action Cable, application Pub/Sub or third Redis service exists in the baseline.

A cache-Redis outage falls back to PostgreSQL for cache reads. It MUST NOT change authorization, state, ordering, score, entitlement or retry winners. Queue-Redis failure follows the separately persisted Sidekiq dispatch/recovery contract and never falls through to cache Redis.

The cache catalogue is exhaustive:

| Cache class | Key preimage | Value | TTL | Invalidation |
| --- | --- | --- | --- | --- |
| Active signed global artifact | schema, artifact type/ID/version/content hash | integrity-verified normalized immutable body | 300 seconds | release activation/supersession event; hash mismatch discards |
| Redaction-independent Project projection fragment | schema, Organization, Project, projection name/version, complete source-version hash | structured projection fields plus classifications, never an AuthorizedDTO | 60 seconds | higher committed projection version event |
| Retrieval search page | schema, Organization, Project, query digest, index/projection version, classification ceiling, cursor | ordered IDs and rank values only | 30 seconds | index/projection version change |
| Static deterministic presentation dictionary | schema, locale, template/label artifact version/hash | human-authored labels/templates | 300 seconds | artifact supersession |

No other cache class is allowed without updating this catalogue. In particular, the application MUST NOT cache Session validity/activity, raw token/digest, Authorization Decision allow/deny, OrganizationMembership, Role/Access Policy result, Support Session, entitlement counters/reservations, idempotency winner, mutable aggregate, current-pointer winner, secret/material, Evidence payload, AI/provider response, Notification body, Export retrieval authority or object-store URL.

Authorization and redaction always run after a projection/search cache hit using current database versions. Cache keys use canonical bytes and SHA-256 for unbounded bodies; they never contain raw email, secret or free text. Cache writes occur after commit. Deletion/retention work deletes eligible cache keys by exact namespace/version and never treats cache eviction as deletion completion evidence.

Redis locks, `SETNX`, cache `add`, Sidekiq uniqueness and process mutexes are prohibited as correctness controls.

## Query Budgets And N+1 Prevention

### Common limits

- Collection default and maximum page size is 50 records. A client value above 50 is rejected by the physical query schema; it is not silently raised.
- Collections use keyset cursors over the declared stable order plus UUID tie-breaker. Offset pagination is prohibited.
- A detail query returns at most 100 inline child summary rows; further children use their registered collection query/cursor.
- The security prelude uses the budget defined above and is counted separately from the application query budget.
- Each authorized read/query transaction sets `statement_timeout=450ms` and `lock_timeout=250ms`. The sole read exception is the registered internal Retrieval search statement, which has `statement_timeout=750ms` and the same `lock_timeout=250ms`; its handler may execute that statement once per Check-stage request. Each command or worker checkpoint transaction sets `statement_timeout=5s` and `lock_timeout=1s`, reduced when the owning Volume I deadline has less time remaining; these values never raise a stricter workflow deadline. Migration and registered lifecycle-batch roles use only their separately declared deployment timeouts. A controller/presenter never changes these workload-class settings.
- The application-query portion targets at most 300ms p95 and server render/serialization at most 100ms p95, leaving transport margin inside QA-REQ-005's provisional 500ms p95.
- Presenters and serializers execute zero SQL.

## Background And External Work

Network calls, DNS, crawling, object storage, PDF generation, AI calls and provider SDK work never occur in an open database transaction or synchronous presenter/query. Commands persist immutable intent/checkpoint state and durable dispatch rows. Every Sidekiq invocation carries exactly the Background Processing scalar envelope: schema version, Organization ID, work type, work ID, product generation, claim generation, correlation ID and causation ID; the handler reloads all other state.

Synchronous HTML/API paths do not wait for high-cost workflow completion. They return the committed accepted result and expose status through the registered projection/Frame. Background concurrency and retry cannot exceed the workflow's persisted entitlement, timeout or retry contract.

## Export Retrieval Checkpoints And Streaming

Export retrieval uses server-mediated streaming only. There is no public, anonymous, reusable or presigned object URL.

The persistence schema provides `export_retrievals` as `T-CHK`: identity and authorization-input fields are immutable, while a trigger permits only the declared monotonic `intent -> streaming -> complete|incomplete|denied` checkpoints and associated result fields.

The exact path is:

1. **Checkpoint A — retrieval intent:** in a short authenticated transaction, reauthorize Session, Account, Organization, `export.retrieve`, requester-as-recipient, Export state, frozen manifest, current field permissions and current Export Policy; apply expiry equality; append a pending `export_retrievals` attempt with object/digest/size references and a 60-second internal start deadline; commit.
2. **Open without emission:** outside a database transaction, open the private object using server credentials, verify metadata, expected byte size and digest-capable stream, but emit zero client bytes.
3. **Checkpoint B — stream start:** in a second short authenticated transaction, lock the Export/retrieval attempt and repeat the complete current authorization and expiry/revocation/policy check. At equality expiry wins. On success atomically set `started_at` and outcome `streaming`; on failure terminalize the attempt, close the object and emit zero bytes.
4. **Stream:** after Checkpoint B commits, stream with backpressure in 64 KiB maximum chunks. Set `Content-Disposition: attachment`, the registered media type, exact `Content-Length`, `X-Content-Type-Options: nosniff`, `Cache-Control: private, no-store`, and no `Accept-Ranges`. The application never buffers the complete package in web-process memory.
5. **Terminal record:** after EOF or disconnect, append actual bytes sent, completion time and exact transport outcome in a short idempotent transaction. EOF with the expected byte count is complete; disconnect/short write is incomplete and never changes the immutable package or consumes another generation.

Revocation, policy contraction or expiry before Checkpoint B emits zero bytes. Checkpoint B is the durable authorization boundary for a stream already begun; later revocation prevents every new retrieval and is recorded against an in-progress transport but cannot retract bytes already emitted. Exact command replay uses the same logical retrieval/result and records a new stream-attempt checkpoint only after current reauthorization; a deliberately new `Idempotency-Key` creates a new authorized retrieval command/attempt against the same immutable Export. Neither path creates a new Export generation or entitlement charge.

## Performance And Resource Controls

- Puma request threads, Sidekiq concurrency and database pool sizes MUST be chosen together so the sum of possible checked-out connections per dyno never exceeds its pool and deployment database allocation.
- Web requests never perform unbounded collection serialization, full-table count, unbounded `includes`, synchronous Export generation or provider retries.
- Gzip/Brotli may compress HTML/JSON/static text at the edge; already compressed Export members and provider bodies are not recompressed in Rails.
- Dashboard/history use current/immutable projections and indexed keyset access; they never recompute a score, crawl, Check, AI output or full event history during read.
- no Action Cable, WebSocket, server-sent-event or background-polling path exists; protected output is fetched only through bounded authorized HTTP queries.
- PostgreSQL query plans for registered queries are captured against production-shaped fixtures; a sequential scan of an unbounded tenant/history table or sort spilling beyond the fixture work-memory gate fails the performance fitness test.
