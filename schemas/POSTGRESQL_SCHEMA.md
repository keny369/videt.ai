# PostgreSQL Schema

## Status And Database Baseline

- Status: Volume II Implementation Architecture Pass 001; complete for unblocked behavior
- Behavioural baseline: immutable tag `v1.3-volume-i-corrected`
- Engine: Heroku PostgreSQL 17; Heroku controls the minor patch
- Encoding/collation: UTF-8, database and connection time zone UTC, deterministic `C` collation for canonical keys
- Extensions: `pgcrypto`, `citext` is not used, `pg_trgm`, `btree_gin`
- ORM: Rails Active Record for persistence adapters only

This document fixes table ownership, columns, constraints, indexes, partitions, locking, tenancy, retention and migration behavior. The pre-Organization, platform-wide and cross-Organization event/audit scope described in the [Volume II Index](../specification/volume-ii/INDEX.md) remains an upstream product blocker; no migration may guess that nullability, sentinel identity, selected tenant, duplication or omission. Credential rotation, reassessment trigger execution, the last-admin-blocked Role expiry branch, Document quarantine/retirement and the ambiguous second-Issue fingerprint-collision branch are independently fail-closed under `UPSTREAM-V1-CREDENTIAL-ROTATION-TOKEN-009`, `UPSTREAM-V1-REASSESSMENT-TRIGGER-EVENT-010`, `UPSTREAM-V1-ROLE-EXPIRY-BLOCKED-EVENT-011`, `UPSTREAM-V1-DOCUMENT-LIFECYCLE-012` and `UPSTREAM-V1-ISSUE-COLLISION-013` as specified below.

## Type And Column Conventions

### Identifiers

- Every unpartitioned stored row uses one application-generated UUIDv7 `id uuid PRIMARY KEY`. That UUID is the default opaque API/event row identifier. Only the explicit semantic/external-ID dictionary entries and the Invitation's separately defined 32-byte public acceptance reference are additional identities; neither replaces or changes the UUID primary key. A partitioned append-only row uses `id uuid NOT NULL` plus the partition timestamp in its composite primary key and an unpartitioned registry whose `id` is the globally unique logical row identifier.
- Relational foreign keys use `uuid`; semantic and provider identifiers use only the explicitly qualified text columns below. Polymorphic audit/event F1-row references use `entity_type text` plus `entity_id uuid` and deliberately have no foreign key so retention can remove the target without rewriting evidence.
- UUIDs are never accepted as proof of access and are never sequential integers.

### Time, numbers, hashes, and text

- Instants are `timestamptz(6)` and names end in `_at`; deadlines use `_due_at` or `_expires_at`.
- Durations and counts are integer base units: `integer` where bounded below 2.1 billion, otherwise `bigint`.
- Bytes use `bigint CHECK (value >= 0)`.
- Confidence is `numeric(5,4) CHECK (value BETWEEN 0 AND 1)`.
- Unrounded score arithmetic is `numeric(18,10)`; displayed score is `numeric(4,1) CHECK (value BETWEEN 0 AND 100)`.
- Rational weights use `weight_numerator bigint` and `weight_denominator bigint CHECK (weight_denominator > 0)`.
- SHA-256 values use `bytea CHECK (octet_length(value) = 32)`. HTTP/API adapters encode them as lowercase hexadecimal.
- Canonical normalized email, host, URI, reason code, permission, state, type, and semantic version are `text`. PostgreSQL enum types are prohibited; each finite vocabulary has a `CHECK` constraint so expand/contract migrations remain possible.
- Human free text uses `text` with application Unicode-NFC/scalar validation and a database byte-length ceiling as a defense in depth.
- Nested immutable contract bodies use `jsonb` only where this catalogue says `payload`. Required identity, tenant, relationship, state, version, deadline, ordering, uniqueness, and query fields remain relational.
- Human explanations are stored only in explicitly named `human_rationale` or human-description columns. A `transition_reason_code`, `decision_reason_code`, terminal `reason_code` or root Event reason is a nullable machine token constrained to the exact applicable Volume I enumeration; it is never populated from, normalized from, hashed from or replaced by human rationale. When Volume I requires human rationale but defines no machine transition reason for the accepted edge, the rationale persists and the machine/Event reason is null.

Large bytes/text beyond the dictionary ceiling are a private Stored Object reference plus digest, never an oversized database field.

## Tenant Isolation And Database Roles

F1 uses one shared schema. Every tenant-owned table has `organization_id NOT NULL`; every Project-owned table also has `project_id NOT NULL`. Tenant parents expose `UNIQUE (organization_id,id)`. Every Project-owned parent additionally exposes `UNIQUE (organization_id,project_id,id)`, and every Project-owned child-to-parent foreign key contains all three values. A direct Project reference uses `(organization_id,project_id) -> projects(organization_id,id)`. These constraints, rather than a separate Project lookup or application assertion, prevent a same-Organization cross-Project child link.

Database roles are exact. `f1_runtime` is a `NOLOGIN` group and never owns an object:

| Role | Authority |
| --- | --- |
| `f1_schema_owner` | owns schema/tables; used only by reviewed release migrations |
| `f1_runtime` | common `NOLOGIN` grants through RLS; no table ownership or `BYPASSRLS` |
| `f1_web` | login member of `f1_runtime`; registered browser/API tables and functions only |
| `f1_worker` | login member of `f1_runtime`; tenant job/outbox tables and registered product functions only |
| `f1_platform_worker` | login role for signed release, scheduler and cross-tenant bridge metadata; no direct tenant-table scan and no `BYPASSRLS` |
| `f1_lifecycle` | login role; manifest claim plus the one fixed deletion function only, with no arbitrary tenant `DELETE` |
| `f1_readonly_ops` | sanitized operational views only; no raw tenant or secret tables |
| `f1_backup` | Heroku-managed backup role; no application use |

Every tenant table, including `T-IMM`, `T-MUT`, `T-CHK` and `PT-IMM`, has `ENABLE ROW LEVEL SECURITY` and `FORCE ROW LEVEL SECURITY`. Application code cannot make tenant context authoritative by executing `SET`, `SET LOCAL`, `set_config`, or a raw SQL wrapper.

The schema owner defines exactly six reviewed context-entry functions: `f1_enter_human_context(session_token_sha256,correlation_id)`, `f1_enter_tenant_service_context(service_jwt_binding_id,organization_id,correlation_id)`, `f1_claim_dispatched_work(schema_version,organization_id,work_type,work_id,product_generation,claim_generation,correlation_id,causation_id,queue_name,worker_process_id)`, `f1_enter_receipt_entry_context(entry_handle_sha256,provisional_organization_id,correlation_id)`, `f1_enter_scoped_security_context(session_token_sha256,work_dispatch_binding_id,organization_id,support_session_id,correlation_id)`, and `f1_enter_mailgun_webhook_context(authenticated_webhook_binding_id,delivery_correlation_sha256,claimed_delivery_id,replay_generation,provider_message_id_sha256,correlation_id)`. Each is `SECURITY DEFINER`, owned by `f1_schema_owner`, revoked from `PUBLIC`, granted only to its named runtime role, and has `search_path=pg_catalog,<fixed_application_schema>`. The first five validate the authoritative Session/service-authentication binding/dispatch binding/receipt-entry/Support Session rows and current scope before returning a proved transaction-local identity. The tenant-service function accepts only a current `service_jwt_binding` and derives the Service Identity from it. For dispatched work, envelope `work_id` is the global restricted Work Dispatch Binding ID. The function resolves that row before RLS, byte-compares every remaining envelope field plus actual queue and worker process, derives its non-caller-selected scope/service proof internally, uses that proof in compiled fixed branches to compare-and-swap the exact forced-RLS source and target owner generations to the worker, and returns success only after updating the binding in the same transaction; any mismatch raises and rolls the transaction back. It accepts no dynamic identifier or caller-selected scope. The scoped-security function requires exactly one of Session token digest or already worker-claimed Work Dispatch Binding ID, derives its actor/service from that restricted locator, then validates the exact active Support Session and Organization scope. No function trusts a caller-supplied actor or Service Identity ID. The receipt-entry function first resolves the no-direct-grant digest locator, then establishes proof and validates the forced-RLS Receipt. Grant issuance has no Organization; Invitation/sign-in must equal the handle's Organization binding; self-service accepts one nonnull provisional Organization that is absent from `organizations` and binds it to the consuming Grant before the first tenant insert. The Mailgun function is described below and derives Organization, Integration, Delivery and attempt exclusively from an authenticated restricted locator. Each function writes a transaction proof computed inside PostgreSQL from the current transaction ID, validated identities, context kind and a schema-owner-only key. The function returns only success/failure and no proof value.

`f1_current_organization_id()` is `STABLE`, `SECURITY DEFINER`, has the same pinned search path and grants, and returns a UUID only when the stored proof validates and `app.organization_id` is a canonical UUID according to `pg_input_is_valid`. Missing, blank, malformed, raw-set or proof-mismatched context returns null without raising. Equivalent private helpers validate the actor, service, bootstrap principal and Support Session. Tenant select/insert/update/delete policies use both `USING` and `WITH CHECK` and require:

```text
organization_id = f1_current_organization_id()
```

Project-scoped operations also require the Project to resolve through the composite same-Organization keys above. Missing, empty, malformed, raw-set or forged transaction context matches no row and never raises a cast error. Request/job entry points open a transaction and call exactly one context-entry function before any authoritative lookup. Connection checkout and checkin execute `RESET ALL`; the first statement after checkout asserts every `app.*` setting is absent.

Pre-Organization bootstrap functions compare `bootstrap_principal_digest` only through the validated receipt-entry helper; a caller-supplied setting never matches. The tenant-creation transaction generates the Organization UUID first and passes it to `f1_enter_receipt_entry_context`; that function binds the proof to the consuming Grant, command and absent generated Organization identity before tenant inserts. It cannot target an existing Organization. There is no RLS bypass.

Cross-Organization support and investigation process one Organization per transaction with its exact Support Session. Control-plane bridge rows are global restricted metadata; they do not grant a query that sees several Organizations at once.

### Table security classes

| Class | Examples | Direct roles | Enforcement |
| --- | --- | --- | --- |
| tenant | every `T-IMM`, `T-MUT`, `T-CHK` and `PT-IMM` row | `f1_web`, `f1_worker` only as registered | forced proof-validating RLS plus same-Organization/composite Project FKs |
| pretenant | Identity Receipt identities/consumptions, Bootstrap Grants and scoped idempotency | `f1_web` receipt-bound functions; approved identity service | forced proved-principal/Receipt policy; no Organization fallback |
| release | Check/catalog/template/policy/playbook/adapter approval bytes | read by runtime; write only `f1_platform_worker` release functions | immutable version/digest/signature and active-head function |
| platform control | global service identities, scheduler leadership and dead-letter administration | `f1_platform_worker` registered functions | no tenant payload and no arbitrary tenant query |
| restricted mixed-scope ledger | Identity Flow/Session/JWT locators, command/idempotency/result rows, work claims, and event/audit/provider registries | no direct runtime table grant; exact registered functions only | function validates proved flow, tenant or bootstrap context, row scope variant, immutable hashes and returned-field authorization |
| cross-tenant bridge | Incident, Investigation, LegalHold and deletion bridge identities | `f1_platform_worker`/`f1_lifecycle` registered functions | global row contains scope metadata; tenant payload read one Organization/RLS transaction at a time |
| sanitized operations | bounded health/queue/aggregate views | `f1_readonly_ops` | security-barrier views; no IDs, customer text, secrets or tenant payload |

No login role receives DML for a whole class by wildcard. Migration grants enumerate tables/functions from the application registries; architecture tests compare actual grants with that manifest.

The nominally global pretenant tables have RLS enabled and forced despite using a `G-*` column set. Their policies call the proof-validating receipt/principal helper and have no tenant fallback. `identity_entry_handles`, `session_token_registry`, `invitation_reference_registry`, `mailgun_delivery_locators` and the other restricted mixed-scope locators are not pretenant data tables: they grant no direct table access at all, and their registered `SECURITY DEFINER` function accepts only the lookup digest or an already authenticated binding, establishes proof where required, and then validates the authoritative forced-RLS row. Other restricted ledgers/registries likewise validate proved context and the exact row variant internally. `FORCE ROW LEVEL SECURITY` on tenant tables still applies to schema-owner functions.

The elected scheduler never scans or claims a tenant target directly. It calls `f1_prepare_dispatch(source_kind,source_id,scheduler_process_id)`, a separate reviewed `SECURITY DEFINER` function owned by `f1_schema_owner`, revoked from `PUBLIC`, granted only to `f1_platform_worker`, and pinned to the qualified search path. `source_kind` is limited to Scheduled Action or Outbox Message. The function validates the current singleton scheduler lease and eligible global restricted source, derives scope/service/mapping entirely from that source, establishes an internal proof, uses the compiled fixed action/consumer branch to claim the source and any specialized forced-RLS target with independent generations, inserts or exact-replays the Work Dispatch Binding, and returns only its fixed scalar envelope plus queue. It accepts no Organization, Service Identity, target table/row, queue or payload from the caller and executes no dynamic SQL; any mismatch rolls the transaction back.

Managed-identity flow persistence is likewise function-only. `f1_begin_identity_flow` generates independent 32-byte state and nonce values with `gen_random_bytes`, stores only their SHA-256 digests and the validated route/configuration binding, and returns the raw values exactly once to the authentication adapter; SQL/log instrumentation redacts the result and parameters. `f1_consume_identity_callback` receives only state/nonce/JWS digests plus the already cryptographically validated normalized claim tuple and validation-key identity, locks the digest row, rechecks exact flow/configuration/purpose/expiry, and commits Flow terminal state, immutable Receipt and Entry Handle together. It can alternatively terminalize the matched Flow with one closed failure reason and no Receipt/Handle. Both are pinned-search-path `SECURITY DEFINER` functions, revoked from `PUBLIC` and granted only to the named authentication entry role. Raw compact JWS/form body/state/nonce is never a function argument that persists, and a second callback cannot create or replace any row.

Invitation entry uses one additional restricted resolver, not a tenant scan. Rails first validates the public reference as exactly 43 unpadded base64url ASCII characters with the canonical single encoding that decodes to 32 random bytes, computes SHA-256 over those decoded 32 bytes, discards both raw forms after the request, and calls `f1_resolve_invitation_reference(opaque_reference_sha256,correlation_id)`. That function is `SECURITY DEFINER`, owned by `f1_schema_owner`, has the pinned search path, is revoked from `PUBLIC`, and is granted only to `f1_web`. It performs one fixed unique-index lookup against `invitation_reference_registry` and the same fixed projection for hit and miss; there is no Organization argument, fallback query or tenant-table scan. It returns the Organization UUID and internal Invitation surrogate UUID only for an active, unexpired, byte-consistent locator so the server can create the purpose-bound managed-identity Flow. All misses, nonactive/terminal rows, expiry equality, digest mismatch and synchronization failure return the same null binding and the route emits the same `invitation_not_active` representation. The resolver returns no target email, role, scope, Organization name or state detail. After identity validation, only `f1_enter_receipt_entry_context` may establish tenant proof and it requires that exact Organization/Invitation/reference binding. Every locator, Flow binding, Entry Handle binding, Invitation row, audit/log redaction and event identity uses this one decoded-byte digest; when exposed as an identity it is its lowercase 64-character hexadecimal encoding. No digest of the 43 ASCII characters is stored or accepted.

Mailgun ingress has a two-step restricted proof. `f1_record_mailgun_webhook_authentication(provider_timestamp,token_sha256,authenticated_content_sha256,signature_key_artifact_id,signature_key_version,signature_key_reference_sha256)` may be called only by the provider-ingress path running as `f1_web` after the adapter has globally validated the five-minute Mailgun HMAC against the exact signed `mailgun-email-v1` webhook-key reference; it is `SECURITY DEFINER`, schema-owner-owned, pinned-search-path, revoked from `PUBLIC`, granted only to `f1_web`, independently requires the supplied key tuple to equal that active signed artifact, assigns `received_at` from the PostgreSQL transaction clock, and atomically inserts or exact-replays one `provider_webhook_token_bindings` row. It accepts no Organization, Integration or Delivery. Exact byte-equal authenticated replay returns the existing binding; authenticated reuse of the token with different content inserts one restricted `provider_webhook_token_conflicts` row only when the first resolved binding proves scope, and establishes no context. The same transaction for a new/exact binding then calls `f1_enter_mailgun_webhook_context` with digests of the authenticated normalized user-variable correlation token and provider message ID plus the claimed Delivery UUID/replay generation. That context function has the same ownership/search-path/revocation controls and is granted only to `f1_web`. It locks the binding, performs one fixed indexed lookup in `mailgun_delivery_locators`, requires a nonnull pre-submission Integration binding and exact Organization/Integration/Delivery/attempt/correlation/generation equality, and either matches the already bound provider-message digest, atomically fills the sole current submitted-unbound locator, or exact-replays the byte-equal previously resolved tuple. It records the locator on a new authentication binding and derives the Organization/Integration/Delivery proof internally before any forced-RLS Provider Event write. An unknown/ambiguous/mismatched locator, terminal-without-submission attempt, reused authentication token with different content, or provider-message collision fails generically and establishes no context. Neither function exposes a query over tenant tables, trusts an Organization/Integration supplied by webhook content, or grants direct access to either restricted locator table.

## Foreign-Key And Deletion Rules

- Default foreign-key action is `ON UPDATE RESTRICT ON DELETE RESTRICT`.
- `ON DELETE CASCADE` is permitted only for the explicitly owned join/detail tables named in this document and only when parent and child share one retention class.
- A nullable lifecycle link uses `ON DELETE SET NULL` only where Volume I permits the reference to disappear; baseline schema uses retained opaque references instead, so no core relation uses implicit `SET NULL`.
- Domain history, Evidence, Issue/score lineage, event, audit, approvals, manifests, and custody references never cascade.
- There is no generic `deleted_at`, Paranoia/discard gem, default scope, or hidden tombstone state. Logical removal uses the exact Volume I state. Physical destruction is performed only by `DataLifecycle` against a frozen manifest.
- Object bytes live in private storage. Database rows store an immutable key/reference, digest, encryption-key reference, classification, retention class, size, media type, and lifecycle status.

The bootstrap-only circular links among Organization, creator Account, active Access/Entitlement policies, BillingEntity and Plan Assignment use named composite foreign keys `DEFERRABLE INITIALLY DEFERRED`. They are the only initially-deferred domain FKs. The bootstrap transaction inserts pending rows, links and activates them, and the commit-time constraints require: Organization self-tenant identity; creator Account same Organization and active; one active OrganizationAdmin Assignment; active byte-exact Access/Entitlement policies; BillingEntity same Organization and active; and active Plan Assignment pointing back to that BillingEntity. A separately committed pending graph cannot satisfy the checks and rolls back.

### Asynchronous claim owner registry

Every Sidekiq Job Catalogue entry has exactly one physical lease row. `event_consume` claims its `outbox_messages` route row; `scheduled_action_dispatch` claims `scheduled_actions`; `verification_observe` claims `verification_attempts`; `crawl_fetch` claims `fetch_attempts`; `ingest`, `parse`, `index`, and `check_execute` claim their corresponding attempt table; `evaluation_advance` claims `evaluation_stage_checkpoints`; `delivery_execute` and `delivery_reconcile` claim their corresponding Delivery attempt/reconciliation table; and `investigation_collect` claims `investigation_collection_checkpoints`.

The remaining exact work types—`crawl_orchestrate`, `score_publish`, `recommendation_generate`, `projection_build`, `provider_event_consume`, `entitlement_reconcile`, `export_generate`, `incident_observe`, `lifecycle_delete`, `object_destroy`, `partition_maintain`, and `invariant_sweep`—claim one `work_executions` row whose immutable owner reference is the Job Catalogue's durable idempotency authority. No handler may choose a different claim table, use a domain row lacking `WORK-CLAIM` as a lease, or hold two transport leases for one invocation. There is no separate `notification_route` work type: `event_consume` executes `notification_route_v1` and owns the resulting Notification/Delivery writes.

Every row named as a direct claim owner includes `WORK-CLAIM`, even when its domain checkpoint columns have a stricter write-once trigger. Scheduler ownership and receiver ownership are two phases of the same owning row and same claim generation, transferred by compare-and-swap; acknowledged enqueue does not create or release a second transport checkpoint. Claim recovery increments only `claim_generation`; product/retry/attempt/replay generations remain unchanged.

Every enqueue first creates or exact-replays one `work_dispatch_bindings` locator whose ID becomes the envelope `work_id`. This registry is not a second lease: its state mirrors whether that exact source/target generation is issued, worker-claimed or terminal. Except for event consumption, every binding names the one Scheduled Action that made immediate or delayed work reachable. `f1_claim_dispatched_work` resolves the binding by envelope `work_id`, validates every other envelope field, the binding's fixed action-kind/work-type/queue/service mapping, caller database role, nonexpired lease, worker process ID, Scheduled Action/Outbox source generation and target row's complete scope/product/claim tuple; its static branches transfer both action and specialized direct owner to the worker atomically, or transfer the single Scheduled Action for `scheduled_action_dispatch` and single Outbox Message for `event_consume`. Completion and enqueue-failure recovery likewise terminalize/release both or neither. A stale/expired/terminal binding, wrong claim generation, queue, process owner, scope, action/target generation or byte-different replay obtains no tenant context and performs no product write. Same-worker redelivery of an already transferred binding resumes the same claim. Claim expiry terminalizes the binding; redispatch creates a new binding ID/generation, while response-lost duplicate enqueue reuses the same binding ID/generation. An active binding cannot be destroyed; after terminalization it is searchable for the 30-day `operational_telemetry` minimum and destroyed at 90 days, while its product result/idempotency authority follows its own longer class.

For a Scheduled Action handoff, `f1_prepare_dispatch` changes `pending -> claimed`, increments the action `claim_generation`, sets its scheduler owner, `claim_phase=scheduler` and 30-second lease, and inserts the Work Dispatch Binding before enqueue. For a specialized work type that same transaction independently claims the fixed direct-owner target and stores its target claim generation; it changes neither row if either claim fails. Redis acknowledgement is followed by a compare-owner/generation transaction that changes the action to `dispatched`, increments `dispatch_attempt_count` and records `dispatched_at` only if that scheduler claim still owns it. The receiver resolves the binding by envelope `work_id` and accepts only its byte-equal envelope with the source in `claimed` or `dispatched`; in one transaction it compare-and-swaps both source and specialized target owners/generations from that scheduler to itself, sets `claim_phase=worker`, changes the action to `dispatched` and records `dispatched_at` when absent, and renews both leases before product work. Generic `scheduled_action_dispatch` has no second owner row. Thus receipt before or after scheduler acknowledgement is valid; acknowledgement after receiver transfer is a no-op and cannot overwrite worker ownership. Enqueue failure returns the action to `pending` and releases a specialized target only when that scheduler still owns every bound generation and `dispatched_at IS NULL`; otherwise neither changes. A duplicate with the same worker ownership resumes; every other owner/generation or terminal state exits without product work. An expired worker claim on a dispatched row is recovered and the same action/product target identity is re-enqueued under new transport generations; it is never changed to a new product schedule generation.

For event consumption, `outbox_messages` is the sole required-consumer route and the sole `event_consume` claim owner. The scheduler claims `pending`, or `published` without its exact consumption for at least 60 seconds, in `(available_at,id)` order; it increments the claim generation, sets scheduler phase and enqueues the fixed delivery-queue envelope. Its acknowledgement sets `published`/`published_at` only while the same scheduler owner/generation remains. The receiver accepts that same generation in either `claimed` or `published`, compare-and-swaps scheduler ownership to worker ownership, sets `published`/`published_at` when absent, renews the lease, and then atomically performs the idempotent Notification/Delivery writes, inserts `event_consumptions`, and sets the route `consumed`/`consumed_at`. A uniqueness loss reloads the stored consumption. Invalid event major/required shape inserts `event_dead_letters` and quarantines the same route without a Notification write. A pre-ack receiver is therefore processed, not discarded, and a late scheduler acknowledgement cannot overwrite it. No `outbox_dispatch`, separate route-discovery handler or fan-out materialization table exists in the baseline.

Transport quarantine is mechanically distinct from event-contract quarantine. On dispatch attempt six, the owning Scheduled Action or Outbox Message is unclaimed and quarantined with exact reason `redis_dispatch_exhausted`; no Event Dead Letter is created. Only `invariant_sweep` may restore those rows. It reads the last three immutable `queue_transport_health_samples` for the current elected-scheduler lineage, requires three successes at least five seconds apart with no intervening failure under the Background Processing rule, and in one bounded transaction returns at most 100 rows to `pending`, ordered by `(due_at,id)` for Scheduled Actions and `(available_at,id)` for Outbox Messages. It clears current claim/quarantine transport fields, resets `dispatch_attempt_count`, and increments `transport_recovery_generation`; product/action/event identities, due/available time, product and schedule generations, policy, preimage and prior dispatch timestamps do not change and no product Event is emitted. The next scheduler claim creates the new claim generation and Work Dispatch Binding. Any other quarantine reason, including an `event_dead_letters` row, is ineligible and terminal.

The two network-concurrency gate families are PostgreSQL correctness authorities. A registered function acquires the gate row and lowest free slot, inserts/activates the lease, and increments the checked active count in one transaction; release after result or expiry performs the inverse with owner/generation comparison. A deferred constraint trigger proves each gate's count equals its active leases and never exceeds capacity. Mailgun send process loss/lease expiry before `submission_started` releases the slot and same attempt. At or after that checkpoint, the sweeper first records `acceptance_unknown` on the owning Delivery attempt and suppresses resubmission, then releases the slot in the same transaction. A normal send result terminalizes the attempt before release. Reconciliation loss/expiry at or after `request_started_at` records that sequence's read-only dependency result before release and can never send or infer nonacceptance from absence. Verification lease expiry first commits the same observation attempt's declared timeout result, then releases the slot; it cannot create a replacement product attempt. Sweepers use `(state,lease_expires_at,id)` and PostgreSQL time. Redis tokens, process semaphores and cache locks cannot acquire, extend or replace either gate.

## State And Immutability Enforcement

- Mutable lifecycle tables have a vocabulary `CHECK`, `state_version`, and `lock_version`. Application transition services enforce the allowed edge; integration specs exercise every invalid edge.
- An immutable table grants only the operations allowed by its security class: ordinary tenant immutable stores expose registered `INSERT`/authorized `SELECT` without `UPDATE`; release and restricted-global tables use their named functions/read path only. Physical deletion remains through the DataLifecycle database function/role invoked by an authorized manifest worker.
- Checkpoint tables grant column-specific update only through one registered transition function. A trigger rejects change to identity/input/tenant columns, a skipped checkpoint, a decreasing checkpoint version, replacement of a nonnull terminal value or a second terminalization. Claim, start and result therefore remain one physical row without pretending the whole row is immutable.
- Versioned immutable payloads never update. A correction creates a successor row and updates only its serialization/current projection in the same transaction.
- Database check constraints enforce actor/service XOR, required/null field combinations, nonnegative versions/counts, positive artifact versions, digest lengths, and deadline ordering.
- Current pointers use composite same-Organization foreign keys and cannot point to diagnostic/nonpromotable rows.

## Nullable Uniqueness

PostgreSQL's default distinct-null uniqueness is never relied upon for a product identity. The DDL uses `UNIQUE NULLS NOT DISTINCT` for idempotency scope tuples, active Role Assignment tuples including nullable persona, policy scopes, scheduled-action identities and every other identity where null is a semantic value. Where null means a different union variant, separate partial indexes are mandatory:

- Notification Account recipient: unique `(notification_id,account_id)` where account ID is nonnull;
- direct email recipient: unique `(notification_id,email_digest)` where email digest is nonnull;
- Delivery escalation: unique `(delivery_id,generation,kind)` where Delivery ID is nonnull;
- empty-selector escalation: unique `(notification_id,generation,kind)` where Delivery ID is null and kind is empty_selector; and
- actor/service identities use a row `CHECK` for exactly one side plus separate nonnull lookup indexes.

Architecture tests enumerate every nullable column in a unique constraint and fail unless its `NULLS NOT DISTINCT` or partial-index semantics appear in the schema manifest.

No partial-index predicate uses `now()`. Expiry is materialized through an explicit state transition.

## Partitioning

Mutable domain, current projection, Evidence, Issue, score, recommendation, entitlement, and lifecycle tables are not partitioned initially.

The following append-only tables use monthly range partitions on their named timestamp:

- `domain_events.occurred_at`
- `audit_records.occurred_at`
- `provider_events.received_at`
- future high-volume transport attempt telemetry, if separated from canonical attempt rows

Global ID registries remain unpartitioned so uniqueness spans all months. Two future monthly partitions MUST exist before the current month ends. There is no default partition; a missing partition fails loudly and alerts before event acceptance.

Each registry insert and matching partition-row insert occur in the same transaction. A deferred constraint trigger proves registry ID, partition month/timestamp, tenant scope, type and content digest match exactly. Consumers locate a row from the registry timestamp and always join on `(partition_timestamp,id)`; no query scans partitions by UUID alone.

A partition may be dropped only after the retention cursor is eligible, every LegalHold/resource intersection is evaluated, required immutable product history and Audit Evidence has been migrated or preserved, and a Deletion Evidence record is committed. If held and unheld rows share a partition, eligible unheld rows are deleted in bounded batches; the partition is not dropped.

## Optimistic And Pessimistic Locking

- `state_version` is the product-visible expected version and increments on every accepted lifecycle or authorization-relevant mutation.
- `lock_version` is Active Record's internal optimistic-lock column and increments on any mutable-row update, including projection rebuild metadata.
- A command compares the requested `expected_state_version`, then persists with `lock_version`; either mismatch returns the frozen stale-state result and never silently retries as a new command.
- Serialization rows and equality races use row locks in the total order defined by the Rails architecture.
- `FOR UPDATE SKIP LOCKED` is limited to due dispatch, outbox batches, and checkpointed deletion manifests. It is not used to choose a business winner whose order is product-visible unless Volume I supplies the ordering.

## Physical Deletion Execution

`f1_lifecycle` cannot issue arbitrary `DELETE`. It may claim one eligible manifest entry through RLS and call only `lifecycle_apply_manifest_entry(job_id,entry_id,expected_entry_digest,attempt_generation)`. The function is `SECURITY DEFINER`, owned by `f1_schema_owner`, has `search_path=pg_catalog,<fixed_application_schema>`, is revoked from `PUBLIC`, accepts no table/column/SQL text and validates:

1. exact running job/generation and claimed manifest entry;
2. Organization, target, retention class, due instant and entry digest;
3. current active LegalHold intersection;
4. prior outcome absence for that generation;
5. allowed target type from a compiled function branch; and
6. child-before-parent dependency completion.

The manifest builder emits entries in this fixed dependency order: ephemeral secret/key material; staged/derived payload objects; join and projection rows; attempt/checkpoint rows; mutable child lifecycle rows; aggregate rows; then optional tenant root. Immutable product history, Audit Evidence, legal-hold, deletion outcome/evidence and retained opaque references are marked retain rather than passed to a delete branch. A target-type branch uses fixed qualified SQL and same-Organization predicates; row count other than the expected zero/one result raises and records no success.

Private object deletion is a separate checkpoint: the worker verifies the same entry, deletes the versioned S3 object/key material, proves absence/version tombstone, then calls the database function to append the outcome. A timeout or uncertain object result never marks deletion complete. The final transaction reconciles every manifest outcome, writes Deletion Evidence and only then completes the job. Backup tombstone verification remains scheduled through the background-processing contract.

## Migration Sequence And Safety

Migrations use expand/backfill/switch/contract:

1. preflight extension/version/lock-size and replica/backup health
2. add nullable column/table/index/constraint as nonvalid where supported
3. deploy code capable of dual-read or dual-write only when the design requires it
4. backfill in bounded idempotent batches with progress evidence
5. validate constraints and RLS policies
6. switch reads/current pointers
7. observe one release window
8. remove old path in a later release

Rules:

- Large indexes use concurrent creation outside a transaction and a named retry-safe migration.
- New required columns are not added with a volatile table-rewrite default. Backfill, validate, then set `NOT NULL`.
- Table/column rename uses compatibility views or dual fields across releases; never one-step rename for a live interface.
- Destructive migration has a recorded irreversible classification, backup/restore proof, retention/LegalHold assessment, and rollback-forward plan.
- RLS is enabled and forced before any tenant table becomes reachable by runtime code.
- A migration may not disable RLS for application traffic.
- Schema dump is SQL format so extensions, checks, RLS, partitions, generated search columns, and views remain canonical.
- CI migrates from an empty database, the previous release schema, and a production-shaped fixture; it runs rollback only for migrations classified reversible.
